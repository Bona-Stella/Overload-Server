## 0. 최상위 원칙과 구현 경계

> **최소한의 입력으로 점진적 과부하를 관리하고, 성장을 직관적으로 시각화한다.** 입력은 간단하게, 수행과 승인 기록은 정확하게, 예외 처리는 실제 필요 범위만큼만 설계한다.

1. 일상적인 운동에서 추가 입력·불필요한 경고·서버 응답 대기를 요구하지 않는다.
2. 데이터 유실, 계정 간 노출, 권한 우회, 중복 전송, 삭제 데이터 재등장은 기술적으로 막는다. **보안은 개인용 앱이라는 이유로 생략하지 않는다.**
3. 실현 가능성이 낮은 상황을 이유로 엔티티·이벤트·사용자 선택지를 과도하게 늘리지 않는다.
4. UX나 공식 점진적 과부하 자격을 바꾸는 판단은 Codex가 독단적으로 정하지 않고 검토 항목으로 보고한다.
5. **MVP에서 제외:** 디로딩·드랍세트·슈퍼세트 전용 도메인, 제조사별 전 세계 장비 카탈로그, 사용자 클릭 전체 감사 로그, 사전 집계 벤치마크 테이블, 계획 슬롯별 UUID 테이블, 불필요한 실시간 타이머 전송.

### 현재 코드 기준 (Task 006-A 보고서의 2026-10-27 분석, 이후 구현 확인 필요)

- `overload-pwa`: React 19, TypeScript 6, Vite 8. 운동 상태 `WorkoutState.version = 1`은 **로컬 문서 스키마 버전**이며 서버 동시성 버전이 아니다. `localStorage`의 `overload.core.v1`은 개발·목업용 운영 이전 상태.

- `/auth-preview`는 개발 전용 **메모리 목업**, 실제 계정·로그인·OTP 인증이 아니다.

## 1. 확정된 운동 종목·루틴 생명주기

### 1.1 사용자별 운동 종목

- **운영 신규 가입 시 기본 운동 종목 목록만 사용자별 새 UUID로 제공**한다. 사용자 루틴 **0개**, 요일 일정 **비어 있음**, 운동 이력·현재 운동·승인 중량/사건 **없음**, 메모 **없음**, 휴식 등 설정은 기본값. 전체 운동 초기화 시에도 **완전히 동일한 운영 초기 상태**로 재구성한다. 기본 운동 종목은 계정 소유 사본이며 공용 편집 카탈로그는 없다. 구체적인 **기본 운동 종목 이름 목록과 기본 휴식값**은 실제 운영 seed 파일을 작성할 때 명시·테스트하지만 **기존 시연용 루틴·일정·샘플 기록은 절대 시드에 포함하지 않는다**.
- 사용자에게 운동 제조사, 헬스장, 장비 브랜드 입력을 강제하지 않는다. 사용자가 종목 추가·이름 변경·삭제를 직접 관리한다.
- **동일성은 `exercise_definition_id`로 판단한다.** 이름을 벤치프레스에서 스쿼트로 바꿔도 ID를 유지하며 기존 비교 계보를 임의로 나누지 않는다. 이름 UNIQUE 금지; 동일 이름의 다른 ID 허용.
- 활성 루틴에서 참조하는 종목 정의를 삭제하려면 먼저 해당 루틴들에서 제거해야 한다. 삭제 요청 시 사용 중인 루틴을 안내하고 서버에서도 차단한다. 과거 세션에만 등장하는 종목은 목록에서 삭제할 수 있지만, 과거 세션의 이름·계획·수행은 보존한다.

### 1.2 루틴 배치, 제거와 복원

- `routine_weight_placements.id`는 종목 정의 ID와 구별된다. **승인 중량·비교 문맥은 루틴 배치별로 독립**이다. 동일 종목을 한 루틴 안에 여러 번 배치해도 허용한다.
- 배치의 `initial_weight`와 `approved_weight`는 구분한다. 사용자 명시 승인 시 현재 승인 중량 + 승인 사건을 같은 트랜잭션으로 기록한다. '오늘만' 작업 중량은 승인값이 아니다.
- 루틴 이름·운동 순서·세트 수·반복 목표 수정은 기존 배치 ID를 유지한다. 비교 문맥이 달라지면 과거 기록은 보존하되 새 문맥에서 비교 가능한 세션만 공식 기준에 사용한다. **운동 중 다른 종목으로 이동하는 것은 루틴 편집/배치 교체가 아니며 원래 종목 순서가 바뀌었다는 이유로 공식 자격을 제외하지 않는다.**
- 저장 전 편집 취소·되돌리기는 실제 종목 제거가 아니므로 배치 ID가 변경되면 안 된다.
- **저장된 제거:** 배치를 논리 삭제(`deleted_at`), 활성 루틴에서 제외하고 이력과 승인값을 보존한다.
- **같은 사용자 + 같은 루틴 + 같은 운동 종목을 재추가:** 삭제된 배치가 있으면 ‘기존 기록 이어가기’ / ‘새 기준으로 시작’ 선택. 삭제된 후보가 여러 개라면 이름만으로 임의 선택하지 않는다.
  - **이어가기:** 사용자가 지정한 이전 배치 ID를 명시적으로 복원한다. 이전 승인 중량·과거 비교 가능 기록을 그대로 연결; 별도 시작 중량 질문 없음; 복원 자체는 승인 중량 변경 사건을 만들지 않음.
  - **새 기준:** 새 배치 ID 생성, 독립적인 승인 중량·공식 비교 기준 시작. 과거 기록은 삭제되지 않음.
- 루틴 자체 삭제 시 요일 일정을 정리하되 이미 시작한 세션과 과거 수행·승인 사건은 보존. 삭제된 루틴 배치에 대한 신규 승인 변경은 금지하고, 진행 중인 운동의 오늘만 중량 수정은 가능.

### 1.3 운동 계획·수행·공식 기준

- **운동 종료는 명시적 사용자 행동**, 서버 동기화와 별개의 상태. 부분 종료 시 실제 완료된 웨이트 수행만 집계; 유산소의 미완료 처리 규칙 유지.
- **운동 중 종목 이동 UX:** 실제 코드의 **기존 `navigateExercise`/종목 목록 선택 경로**를 재사용하여 원하는 종목으로 즉시 이동한다. 표시용 종목 목록에서는 **최초 계획에 속하고 아직 완료하지 않은 웨이트 종목을 우선** 보여주고, 완료한 종목도 다시 열 수 있게 한다. 최초 계획 소속 여부는 현재 변경될 수 있는 루틴이 아니라 **시작 스냅샷의 세션 종목 ID**로 판단한다. 목록의 표시 순서만 바꾸며 저장된 세션 종목 배열·원래 루틴의 순서·승인값을 변경하거나 서버 도메인 명령/클릭 로그를 만들지 않는다. 현행 **‘현재 종목 교체’는 새 종목 추가 후 기존 종목 제거를 수행하는 실제 계획 변경 기능**으로 확인되었으므로 단순 이동과 이름·UI·명령을 분리한다. 별도 드래그 재정렬 버튼은 도입하지 않는다. 미완료 여부는 최종 유효 완료 세트를 기준으로 계산한다.
- `initial_plan_snapshot`은 세션 시작 시 불변: 당시 루틴/종목명, 배치 출처, 세트 수, 목표 반복 범위, 승인 중량, 순서와 유산소 계획 등을 보존.
- `applied_plan_snapshot`은 진행 중 적용 계획을 표현하고 최초 종료 시 봉인한다. `active_checkpoint`는 타이머·미완료 세트 초안·작업 중량 등의 로컬/서버 복원 문맥이다. 완료된 웨이트 수행의 **공식 원본은 `performed_sets` 관계형 행**; JSONB와 이중 원본으로 저장하지 않는다.
- **Task 006-C 최종 사용자 결정:** 중간 UI에서 세트를 추가·삭제했다는 사실만으로 기준 자격을 박탈하지 않는다. **최초 계획과 현재 최종 유효 기록**을 비교한다. 계획 3세트 → 4세트 추가 → 추가 기록 삭제 후 정상 3세트가 남으면 정규 비교 후보가 될 수 있다. 계획 3세트 → 유효 2세트면 공식 기준 제외. 삭제된 수행은 통계에도 포함하지 않는다. 계획 슬롯 UUID·탭 클릭 이벤트 이력은 구현하지 않는다.
- 종목의 정상 승인 중량, 동일 배치·종목 ID, 동일 목표 세트 수 및 최소/최대 반복 문맥, 세션 전체의 당초 계획 완료 여부와 추가 유효 수행 여부 등을 일관되게 검사한다. **원래 계획된 다른 웨이트 종목을 지워 미완료를 완료로 둔갑시키면 안 된다.** 목표 반복 범위 내의 실제 반복 횟수는 비교 성과로서 서로 달라도 된다. 오늘만/혼합 중량은 정규 기준 후보에서 제외. 유산소 건너뛰기는 웨이트 자격을 막지 않는다.
- **운동 진행 중 승인 중량 변경:** 시작 계획의 승인 중량 60kg을 보존하되, 실제 첫 세트 완료 전에 62.5kg으로 **명시 승인**하여 원계획 모든 웨이트 세트를 62.5kg으로 정상 수행했다면 **62.5kg 비교 문맥의 공식 후보 인정**. 60kg 1세트 수행 후 62.5kg으로 바꿔 혼합 수행했다면 제외. 단순 ‘오늘만’ 중량 변경은 공식 승인값이 아니다. **승인 사건은 불변 기록**, 새 완료/현재 평가에는 최종 유효 승인 문맥을 적용한다. 최초 계획 중량이 달랐다는 사유만으로 거부하지 않는다.
- 공식 기준 배열은 **단일 과거 세션의 전체 유효 반복 배열**만 사용한다. 서로 다른 세션의 최고 세트 조합 금지. 최고 기준과 최신 수행에 따른 감량 검토는 별개 개념이며, 실제 승인 중량을 자동 증감하지 않는다.
- **운동 종료 후 사용자 편집 범위:** 기존 세션 종목의 **실제 완료 세트 중량·반복 수 정정**, 세트/세션 삭제는 허용; **최초 또는 종료 당시 없던 새로운 운동 종목을 임의로 추가하는 편집 UI는 MVP에서 제공하지 않는다.** 계획·목표·배치·종목 순서의 사후 변경도 금지한다. 이는 운동 중의 자유로운 종목 추가와 구분된다. 오프라인 강제 이전 때문에 기존 세션 종목에서 누락된 유효 수행 세트를 사용자 선택으로 복구하는 것은 **일반 사후 종목 추가가 아닌 특별한 충돌 복구 명령**으로 허용한다. 복구 시 봉인 계획은 수정하지 않는다.
- 완결 후 수행 중량·반복 횟수의 정정 및 개별 수행/세션 삭제 허용. 변경 전후 값/서버 변경 시각을 `record_change_events`로 저장, 현재 유효 수행에 따라 기준·성장 차트 재평가. **당시의 시작/종료 계획, 최초 종료 시 판단 스냅샷, 과거 승인 사건은 소급 변경 금지**. 현재 평가와 당시 평가를 혼동하지 않는다.
- 새 완료 세트의 반복 횟수는 1 이상; 0kg 허용; 계획보다 많은/적은 수행 자체는 저장 가능하며 공식 기준 후보 여부는 별도 판단. 기존 v1의 0회 기록은 읽기 호환 대상으로 식별하지만 신규 작성 허용 근거가 아니다.
- 유산소는 `ready → running ↔ paused → review → completed/skipped`와 실제 `activeMs`, 자동 원본 `timerMs`, 수동 거리/BPM, 선택적 정정 플래그 등을 유지. 미입력 실제값을 계획에서 추정 생성하지 않는다. 매초 서버 전송 금지.

## 2. 확정된 수치·단위·날짜 정책

### 2.1 중량, 향후 lb 확장

- **MVP의 실제 입력/관리 단위는 kg**. 중량 원본을 보존하고 별도의 환산값을 DB에 저장하지 않는다.
- **향후 lb 직접 입력은 고려만** 하며 지금 UX·DB 변환 구조를 과도하게 만들지 않는다. 사용자가 kg를 kg로, lb를 lb로 관리하는 것이 목표다. 다른 단위 환산은 프론트엔드의 **대략적인 참고 표시**(예: 60kg ≈ 132.3lb)이지 공식 실적·승인 데이터가 아니다.
- lb 직접 입력 기능을 구현할 때는 그때 **원본 단위 식별과 동일·상이 단위 비교 정책**을 명시적으로 추가한다. 지금부터 kg/lb 값을 자동 합산하거나 환산 결과로 기존 승인값을 덮어쓰지 않는다.
- PostgreSQL `NUMERIC` / Java `BigDecimal` 계열을 후보로 유지. **`NUMERIC(10,3)` 및 DB 소수 자릿수 상한은 미확정**. 무분별한 반올림 금지; 기존 kg 입력 규칙에 맞는 형식/현실적인 기술적 범위는 구현 전 검증.
- 반복·세트 수 등에는 **운동 능력에 대한 임의의 비현실적 상한을 만들지 않는다**. 단 형식 오류·NaN/무한대·음수·부적절한 소수·안전하지 않은 숫자 크기 등 기술적 검증은 서버와 DB에서 수행한다.

### 2.2 운동 날짜·타임스탬프

- **공식 운동 날짜(`workout_date`)는 운동 시작 당시의 현지 날짜로 고정**한다. 자정을 넘기거나 오프라인 명령이 며칠 뒤 전송되어도 변경하지 않는다. 운동 한 번을 날짜별 두 세션으로 나누지 않는다.
- 시작/종료 시각은 `TIMESTAMPTZ`와 Java `Instant` 계열; 운동 날짜는 `DATE`/`LocalDate`; 시작 시간대는 IANA 값(예: `Asia/Seoul`) 별도 보존. 서버 수신·변경 시각은 따로 저장한다.
- 기기 시스템 시간대를 사용하며 사용자에게 위치 권한이나 별도 시간대 입력을 요구하지 않는다. 기기 시계가 잘못된 경우/임의 날짜 정정은 일반 기록 수정보다 별도 계약으로 검토한다.

## 4. IndexedDB·Outbox·동기화·기기 제어권

### 4.1 로컬 우선, 서버 ACK

- **IndexedDB + 원자적 Outbox 확정**. 세트 완료 등의 도메인 상태 저장과 서버로 보낼 명령을 **하나의 IndexedDB 트랜잭션**에 기록한다. 로컬 저장이 실패하면 세트 완료로 표시하지 않는다.
- 세트 완료·정정, 승인 중량 변경, 유산소 상태 전이·완료, 세션 종료 등 **실제 상태 변경 시** 백그라운드 전송 시도. 타이머 매초 전송하지 않음. 완료 버튼은 서버 응답 대기 없이 진행.
- 같은 집계(세션/루틴)에서 의존하는 명령을 순차 처리하고 **서버 ACK로 확정된 version**을 받은 후 다음 명령을 송신. 오프라인에서 뒤따르는 명령의 서버 version은 알 수 없으므로 **로컬에서 먼저 의도/명령 ID/선행 의존관계를 저장**하고, 선행 ACK를 받은 뒤 **최초 전송 직전 ACK로 확정 가능한 기대 version과 요청 payload를 영속적으로 봉인**한다. 단, **명령 생성 당시의 계정·dataGeneration·소유권 epoch(또는 세션 생성/정상 이전 등 권한을 부여할 선행 명령에 대한 명시적 의존성)는 생성 시점부터 보존**하고, 최신 서버 epoch를 조회했다는 이유로 옛 명령의 권한을 자동 교체하지 않는다. 전송 이후 재시도는 봉인된 동일 바이트 의미의 명령을 사용한다. 서로 다른 집계를 함께 변경하는 승인 이벤트에는 종속성/두 버전을 원자적으로 처리하는 계약 필요.
- `operationId`는 로컬 명령 생성 시 발급 후 불변이며, **최초 송신에 봉인한 요청**은 이후 재시도 때 payload/expectedVersions/epoch가 동일해야 한다. 서버는 `(user_id,data_generation,operation_id)` 멱등성 확인 + payload fingerprint 검증. **요청 적용·관련 사건·집계 버전·멱등 결과**를 DB에서 하나의 트랜잭션으로 커밋하고 ACK.
- 네트워크/서버 일시 장애는 Outbox 보존 후 백오프 재시도. 응답 유실은 동일 operation ID 재시도. 유효하지 않은 명령·권한/제어권 충돌은 무한 자동 재시도 금지. 서버 ACK의 옛 snapshot이 더 새로운 로컬 입력을 덮어쓰지 않게 주의.
- 단순 오프라인과 인증 만료와 사용자의 명시적 로그아웃을 구별한다. 계정별 `(serverUserId, dataGeneration)` 데이터·큐·조회 캐시를 격리하고, 늦게 도착한 이전 계정 응답이 현재 계정 화면/DB 영역에 섞이면 안 된다.
- IndexedDB는 절대 영구 보존 장치가 아니다. 서버에 ACK받지 못한 기록이 **브라우저 저장소 삭제 시 유실될 수 있음**을 명확히 한다. iOS PWA가 완전히 종료됐을 때 백그라운드 전송을 보장한다고 주장하지 않는다.

### 4.2 수정 제어권·정상/강제 이전

- 한 운동 세션에 서버가 허용하는 수정 기기는 **동시에 하나**. 다른 기기는 조회만 가능. 현재 기기 ID는 인증 증명이 아니며 사용자 principal과 세션 소유권·`ownership_epoch`를 함께 확인.
- 정상 이전: 이전 기기의 대기 명령 ACK·동기화 확인 후 명시적으로 새 기기에 제어권 이전.
- 강제 이전: 기존 기기 오프라인/불능이어도 사용자가 불일치 가능성을 확인하면 마지막 서버 snapshot 기준으로 명시적 제어권 이전 허용. epoch 증가, 구 epoch 명령 거부; **오래된 기기의 로컬 원본은 삭제하지 않는다**. 서버가 오프라인 기기 화면까지 즉시 수정 불가로 만든다는 보장은 하지 않는다.
- 같은 기기의 여러 탭도 하나의 로컬 쓰기 주체로 제어해야 한다. 세션 현재 version·epoch는 최종 방어선이며 device ID 변경만으로 탈취할 수 없어야 한다.

### 4.3 충돌 차이·선택적 복구

- 서버 상태 vs 계정 전용 로컬 원본의 **수행 단위 차이**를 표시, 사용자가 유지할 값을 고른다. 자동 마지막 쓰기 승자·수행 중복 합산·별도 공식 운동 세션 자동 생성 금지.
- 복구는 **현재 서버 version 및 올바른 epoch**에서 새 operation ID로 수행 정정/추가 명령을 제출한다. 과거 구 epoch 명령을 재활용하지 않는다. 원본은 해결 ACK까지 보존한다.
- **원래 계획과 실제 수행은 다를 수 있다.** 이전 기기에만 있는 정상적인 추가 완료 세트는 같은 공식 세션에 반영할 수 있지만 **최초 계획과 종료 당시 계획을 소급 수정하지 않는다**. 공식 기준 자격은 Task 006-C 규칙에 따라 최종 유효 수행으로 재계산한다.
- 기존에 삭제된 세트 ID를 복구하는 경우에는 사용자 명시 선택과 서버의 안전한 별도 복구 명령이 필요하다. 오래된 명령이 tombstone을 자동 해제하는 동작은 금지. **기존 세션 종목의 누락 세트 선택 복구는 허용**하지만, 완료한 세션에 **새 종목 자체를 추가하는 UI·명령은 MVP 범위 밖**이다. 같은 ordinal에 이미 유효 세트가 있다면 사용자에게 차이를 보여주고 별도 정정으로 처리한다.
- 별도 `sync_conflicts` 서버 테이블은 MVP 기본 요구가 아니다. 선택적 복구의 **로컬 보존·재진입**이 먼저며, 브라우저 데이터가 삭제되었는데 서버 미수신 값을 복구해 준다는 약속은 하지 않는다.

### 4.4 API 계약 **초안** (경로/DTO 확정 전)

- 인증: Google OIDC 진입·콜백 / 이메일 OTP 요청·검증 / 현재 사용자·세션 조회 / 로그아웃 / 수단 연결·해제 / 민감 작업 재인증.
- 루틴/설정: 운동 종목, 루틴·배치 추가/제거/복원, 승인 중량, 요일 일정, 메모·휴식 설정.
- 운동: 세션 생성·조회/목록, 세트·유산소·세션 종료 도메인 명령, 제어권 전환(정상/강제), 사후 기록 정정·삭제.
- 동기화: bootstrap/변경 pull(삭제도 포함)/Outbox ACK, 필요시 최신 상태 재조회/재기준화.
- 계정: 내보내기(JSON), 전체 운동 초기화, 회원 탈퇴.
- 작업 명령 후보: `operationId`, 집계별 `expectedVersions`, `dataGeneration`, `ownershipEpoch`(세션 명령), 작업 종류와 payload, 도메인 ID. **오프라인 명령은 생성 당시 계정·generation·epoch 또는 권한을 부여할 선행 명령의 의존성을 보존한다.** 선행 ACK로 기대 version을 확정한 후 최초 송신 요청을 봉인하되, 소유권을 상실한 구 epoch 명령을 최신 epoch로 재태깅하지 않는다. 구 기기 수행은 별도 명시적 선택 복구와 새 operation ID로만 처리한다. user ID는 **서버 principal에서** 판정.
- 응답 결과: 새 적용/같은 명령의 기존 적용 확인, 인증 필요, 입력 검증, 동시성 버전 충돌, 제어권 상실, 삭제/초기화 세대 충돌. HTTP 코드와 JSON 오류 ID/필드별 응답은 Codex 읽기 검증·별도 승인으로 확정.

## 5. 삭제·초기화·탈퇴 및 데이터 보존

### 5.1 일반 수행/세션 삭제

- 개별 세트 삭제는 그 **유효 수행만** 통계·볼륨·기준에서 즉시 제외한다. 최초 계획(예정 세트 수)을 소급 축소하여 완료인 것처럼 만들지 않는다.
- 완료 세션 삭제는 해당 세션의 모든 결과를 현재 기록/차트/공식 기준에서 제외. 해당 세션과 무관하게 이미 발생한 `progress_change_events`나 승인 중량은 자동 수정·역전하지 않는다.
- 삭제 표식(`deleted_at`) 및 정정 전후 사건/작업 결과를 보존해 오래된 기기의 새/재전송 요청으로 삭제된 ID가 부활하지 않게 한다.
- 별도의 일반 사용자용 휴지통, 클릭 로그, 자동 삭제 복원, 과도한 보존 기간 옵션은 MVP에서 제외.

### 5.2 전체 운동 초기화 **(확정)**

- **초기화는 ‘데이터 전부 지워 빈 화면으로 만들기’가 아니라 ‘신규 가입 직후의 초기 상태로 복원’**하는 기능이다.
- 로그인 계정·기존 인증 수단·닉네임은 유지한다.
- 과거 루틴/일정, 운동 종목 편집/개인 추가, 실제 수행/유산소/진행 세션, 승인 중량/변경 사건, 메모, 휴식 설정을 **운동 초기 상태로 재설정**한다.
- 기본 운동 종목은 사용자별 **새 ID로 다시 생성**한다. **루틴과 요일 일정은 모두 비우고**, 이력·진행 세션·승인 값·사건·메모는 없음으로 만든다. 휴식 등 설정은 운영 기본값으로 되돌린다. 가입과 초기화는 **같은 운영 seed 정의**를 사용한다. 기존 **개발 샘플 루틴·일정·기록·기존 mock ID는 사용하지 않는다**.
- 초기화 전 JSON 내보내기 안내, 최근 10분 재인증, 최종 확인. 서버 `data_generation` 증가와 이전 세대 조회/쓰기 차단을 원자적으로 보장. 다른 기기의 구 세대 Outbox를 새 세대로 자동 이관하지 않는다.
- 이전 사용자 운동 데이터와 변경 이력은 파기 대상. 백업/삭제 이력/멱등 정보가 초기화 의미를 훼손하지 않도록 보존·파기 계약은 운영 환경별 추가 검증 필요.

### 5.3 회원 탈퇴와 백업

- 회원 탈퇴는 초기화와 다르다. 재인증·확정 이후 서버 접근/세션 무효화, 계정·인증 수단·운동 데이터 파기 대상. **서버 응답 없이 오프라인 탈퇴 완료를 표시하지 않는다**.
- 동일 이메일로 재가입하더라도 옛 user ID/기록/Outbox 재연결 금지. 이전 오프라인 기기는 다음 서버 재접속 시 탈퇴 상태를 확인해 로컬 데이터를 정리한다. 원격 오프라인 기기에서 즉각 삭제가 보장된다고 표현하지 않는다.
- DB 백업·감사 메타데이터·작업 중 복구 원본의 구체 보존 일수는 **배포 운영 방식이 정해질 때 확정**. 무기한 보존·즉시 완전 파기를 지금 보장하지 않는다. 백업 복원 후에도 삭제·초기화·탈퇴된 데이터가 서비스에서 재노출되지 않아야 한다.

## 6. PostgreSQL 논리 모델·핵심 제약

| 도메인 | 테이블 / 역할 |
|---|---|
| 인증 | `users`, `auth_identities`, `email_otp_challenges`, Spring Session JDBC 관리 테이블 |
| 운동 계획 | `exercise_definitions`, `routines`, `routine_weight_placements`, `routine_cardio_placements`, `weekly_schedule`, `exercise_memos`, `user_workout_settings` |
| 운동 결과 | `workout_sessions`, `session_weight_exercises`, `performed_sets`, `session_cardio_activities` |
| 사건·전송 | `progress_change_events`, `record_change_events`, `sync_operations` |

- 본 표는 **논리 엔티티**, 현재 DB 설치·DDL 완료를 뜻하지 않는다. 서버 물리 스키마 이름과 DTO는 구현 승인 전 검토.
- UUID PK와 필요한 `(user_id,id)` 또는 `(user_id,data_generation,id)` 복합 FK/유일 키, 인증 provider 고유키, `(user_id,data_generation,operation_id)` 멱등성 UNIQUE. 전 자식 테이블에 user_id를 기계적으로 복제하지 말고 **실제 교차 소유권·세대 FK를 검증할 경계**에 적용한다. 요청 user_id를 권한 근거로 신뢰하지 않는다.
- 같은 종목 정의를 같은 루틴에 복수 배치 허용: **`(routine_id,exercise_definition_id)` UNIQUE 금지**. 활성 배치의 정렬 충돌은 DB 부분 유일 인덱스 등으로 제한; 삭제 배치는 순서 제약에서 제외.
- 운동 종목 이름에 UNIQUE 제약 없음. 활성 루틴에서 정의 참조 중이면 종목 삭제 거부; 제거/복원·순서 변경은 같은 루틴 `version` 비교와 트랜잭션으로 처리.
- 루틴·세션 단위 `version`으로 변경 경쟁 보호. 실제 세트/유산소 수정 시 **부모 세션 version이 반드시 함께 증가**하도록 명령 처리. JPA `@Version`이 하위 업데이트에 자동 반응한다고 가정하지 않음.
- `ownership_epoch`와 현재 수정 기기는 `workout_sessions` 컬럼으로 우선 고려; 별도 소유권 테이블은 필요 시에만.
- `session_weight_exercises.id`는 매 세션 새 UUID, nullable `source_placement_id`로 배치 출처를 연결; 출처와 원루틴 삭제로 과거 수행이 연쇄 삭제되면 안 된다. `performed_sets` UUID·ordinal·중량·반복·완료 시각·삭제 표식; ordinal 유일성은 활성 수행 기준으로 검증.
- `initial_plan_snapshot`, `applied_plan_snapshot`, `completion_assessment_snapshot`, `active_checkpoint`는 목적이 다른 **스키마 버전 있는 JSONB**. 수행값 중복 저장 금지. **첫 승인 중량 변경으로 공식 평가 문맥이 바뀌더라도 최초 계획을 덮어쓰지 않는다.** 서버 세션 종목 ID, 출처 배치 ID, 당시 표시명은 구별하여 보존한다.
- `CHECK`: 계획 세트 수 >0, `1 ≤ minReps ≤ maxReps`, 중량 ≥0, 신규 실제 반복 ≥1, 유산소 시간/거리/심박 등 기존 규칙. 숫자 정밀도·기술 상한은 최종 검증. 다중 행 조건과 계정 소유권 전체를 단일 CHECK로 해결한다고 가정하지 않음.
- **승인 중량 변경 + 승인 사건 + 관련 진행 세션 상태 + 버전 + 멱등 결과**는 하나의 서버 트랜잭션. 수행 정정·삭제에도 이전/이후 사건·parent version·멱등 커밋의 원자성 적용.
- 전체 운동 초기화는 user generation 변경과 진행 쓰기의 경쟁을 직렬화. 구 세대 기록을 현재 세대에 삽입·연결하지 않는다.
- 통계·공식 기준은 현재 유효 수행으로 재계산. 별도 benchmarks 테이블은 MVP에 없음. 성능 필요가 확인될 때만 검증된 캐시 도입.

### v0.2 → v0.3 변경 내역

1. **운영 seed 명확화:** 기존 PUSH/PULL/LEGS 포함 개발용 데이터/예시 일정/목업 기록은 운영 계정으로 이관하지 않음. 신규 사용자는 기본 종목 목록만 보유하며 루틴·일정·기록은 빈 상태. 초기화도 같은 상태.
2. **운동 중 중량 승인:** 운동 시작 시점 중량이 달라도 실제 첫 세트 전 새 중량을 명시 승인하고 원계획 정상 세트를 전부 새 중량으로 완료하면 공식 후보 인정. 혼합/오늘만 제외.
3. **운동 중 종목 선택(당시 v0.3의 표현):** 미완료 원계획 종목 우선 제공·즉시 이동 허용. **v0.3.1 최종 코드는 기존 종목 목록/`navigateExercise`를 이용하며, ‘현재 종목 교체’는 실제 계획 변경으로 별도 유지**한다.
4. **종료 후 편집:** 기존 종목의 수행값 정정·삭제 허용. **완전히 새로운 종목을 추가하는 UI는 제외**, 누락된 기존 종목 세트의 명시적 충돌 복구와 분리.
5. **Codex 006-F 결과 반영:** P0 로컬 저장 실패·계정 경계, P1 기준 평가·계보·복원·승인 충돌 및 재검증 테스트.
6. **Outbox 송신 전 봉인 명시:** 오프라인에서 미래 서버 버전을 추측하지 않으며 첫 전송 후 같은 operationId로 페이로드나 기대 버전을 바꾸지 않음.

**본 v0.3.1은 Task 006 최종 설계 기준이다. 프로젝트 저장소 반영·Git Commit·Push·Task 007 구현을 자동 수행했다는 의미는 아니다.**

### v0.3 → v0.3.1 확정 보완 사항 (Codex 최종 검증 반영)

1. **신규 정책 결정 없음:** 운영 가입/초기화, 승인 중량 비교, 완료 후 정정·복구 범위는 v0.3 그대로 확정. 추가 제품 정책 검토 없이 Task 007-1에 착수 가능.
2. **실제 종목 이동 코드 확인:** 기존 `navigateExercise`는 단순 이동이며, ‘현재 종목 교체’는 새 종목 추가와 이전 종목 제거를 동반하는 계획 변경. 미완료 원계획 종목 우선 표시는 종목 목록의 표시 정렬만 변경하며, 실제 루틴·세션 계획은 변경하지 않는다.
3. **Outbox 권한 문맥의 불변성:** 생성 당시 계정/세대/epoch(또는 명시적 선행 권한 부여 명령)를 의도와 함께 기록한다. ACK 후 기대 version 봉인은 가능하나, **구 epoch 명령에 최신 epoch를 붙이는 자동 재태깅은 금지**. 별도 선택 복구와 새 operation ID가 필요.
4. **상태 구분:** 최종 읽기 전용 검증은 제품 설계 일관성과 착수 가능성만 확인했으며, 기존 P0/P1 코드 차이는 여전히 Task 007의 해결 대상. 테스트·빌드는 이번 검증에서 실행되지 않았고, Git 보관·구현도 이 문서 작성 시점에 수행되지 않았다.

**최종 승인 범위:** Task 006 제품 정책 및 설계 확정, 문서 전용 Git 보관 진행 가능. Task 007-1의 구현 작업은 이 명세의 단계적 수용 기준을 따라 별도 작업으로 수행한다. 개발 목업 데이터 파기·운영 이전·DB 변경·서비스 배포는 문서 보관 승인에 포함되지 않는다.
