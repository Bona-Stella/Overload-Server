## 0. 이 문서의 지위와 핵심 결론

### 2026-10-31 후속 사용자 승인 — 현행 보완

아래 보완이 과거 본문의 상충 표현보다 우선한다. 제품 정책 승인과 단계별 실제 구현 상태를 구분한다.

- 편집권은 기존 로그인·CSRF·editorDeviceId·writerEpoch·localRevision으로 관리한다. 별도 editorProof·비밀 기기 토큰/증명 hash·기기 인증 시스템을 만들지 않는다.
- InitialPlan의 유일한 권위 있는 저장 원본은 세션의 불변 JSONB다. 관계형 테이블에 최초 이름·목표·중량·순서를 중복 저장하지 않는다.
- ACTIVE 부분 UNIQUE는 dataGeneration이 아닌 **user_id 단독**이다. 현재 세대 FK·users 잠금과 함께 초기화/구 세대 쓰기를 격리한다.
- 24시간은 START와 **실제 확정 운동 상태 저장**으로만 갱신하는 last_workout_synced_at 기준이다. 조회·중복·takeover·기기 변경·승인 해결 메타만으로 연장하지 않는다.
- 수행 저장 ACK와 승인 적용을 구분한다. 외부 루틴 변경으로 승인 적용이 불가능해도 완료 세트·유산소는 저장하고 승인 요청만 PENDING으로 보존한다. 기존 승인 사건은 삭제하지 않는다.
- 같은 루틴/배치의 오프라인 명시 승인 요청은 고정 UUID와 원래 순서·각 의도를 보존한다. 같은 업로드의 잠금 당시 외부 기준 version을 먼저 검증하고, 내부 선행 승인으로 발생한 증가를 외부 충돌로 판정하지 않는다. 외부 변경이 없으면 순차 승인 전부 정상 처리한다. 미해결 선행 요청의 후속을 임의 자동 적용하지 않는다.
- 승인 순서는 기기 시각이나 UUID 정렬이 아닌 세션 배치별 불변 순번으로 표현한다. 같은 업로드의 공통 기대 routine version을 처리 전 잠금값과 비교하고, 체인의 이전/다음 중량을 순서대로 검증한다. 정상 체인의 사건은 각각 보존하되 루틴 집계 version은 기존 API처럼 실제 변경 트랜잭션당1회 증가시켜 자체 선행 승인을 외부 충돌로 오인하지 않는다. 실제 저장/해결 API·테이블은 세션 계약을 따른다.
- 충돌 해결 재승인은 현재 시점의 **새 명시 승인**이며 소급하지 않는다. 충돌/재승인으로 과거 수행의 승인 문맥을 재작성하지 않는다. 최초 명시 종료 계획/평가는 보존한다.
- 공식 비교는 기존 도메인 자격의 단일 과거 세션 중 **첫 N개 유효 수행 반복 합계 DESC → 실제 명시 종료 시각 DESC → 세션 UUID ASC**다. AUTO_CLOSED는 공식 비교 후보에서 제외하지만 수행 이력·통계에는 남긴다. 첫 N개·추가 실적 보존·자동 중량 증가 금지는 유지한다.
- 기기 시각은 구조적 일관성을 검사한다. 명백한 모순은422 CLOCK_CONTEXT_INVALID로 거절하고 원본/입력을 보존한다. 서버 시각으로 임의 보정하거나 허용 편차를 임의 도입하지 않는다.
- 2026-10-31 3단계 구현 중 사용자 확인으로 평가 정책 A·B를 확정했다. A: 정상 승인·계획 문맥을 충족하는 양수 수행은 목표 반복 미달/초과만으로 비교 후보에서 제외하지 않는다. B: 승인 전 수행했다가 명시 삭제한 세트는 당시 수행/승인 문맥과 삭제 이력을 보존하지만, 현재 유효 첫 N개가 정상 승인 문맥을 충족하면 그 삭제 이력만으로 영구 제외하지 않는다. 재승인으로 기존 수행 문맥을 소급 변경하지 않는다.
- 과거 후보는 실제 명시 종료 시각 `endedAt <= current.startedAt`으로 제한한다. 이번 수행의 권고는 자격 미충족이면 UNAVAILABLE, 첫 N개 중 하나라도 하한 미달이면 DECREASE, 전부 상한 이상이면 INCREASE, 그 밖에는 MAINTAIN이다. 비교 후보 합계 순위와 권고는 별개다. 최고 기준과 최근 약한 수행을 하나의 새 권고 공식으로 합치지 않는다.
- 위 산식은 2026-10-31 사용자 확정의 초기 안내 정책이다. 사용자의 판단을 돕는 권고이며 승인 중량을 자동 변경하지 않는다. 중량 변경은 별도의 명시적 승인을 따른다.
- 4단계 사용자 확정: 종료 후 편집은 expectedVersion으로 분리한다. InitialPlan·봉인 AppliedPlan·최초 평가·승인 사건·최초 수행 문맥은 유지한다. 확인 불가 복구 주장은 UNVERIFIED로 보존하고 공식 평가에서 제외하며 원래 주장/관련 UUID는 복구 이력에 남긴다. 현재 루틴 승인값이나 종료 후 재승인을 과거 수행에 소급 적용하지 않는다.
- AUTO_CLOSED의 closedAt은 서버 확정 시각이다. 사용자가 원본을 확인해 복구한 완료 수행이 그 시각 이후라는 이유만으로 거절하지 않는다. 시작·종목·타이머·선후 관계를 검증하고 원래 sessionId/origin을 유지한다. ACTIVE/FINISHED 전환이나 최초 평가 생성·비교 후보 편입은 없다.
- FINISH 재확인은 최초 종료 버전/식별/평가를 유지하며 현재 버전·승인 결과·삭제 여부를 구분한다. 현재 평가는 조회 시 재계산하고 최초 평가를 덮어쓰지 않는다. 새 영구 요청 영수증은 없다.

실제 구현은 [세션 API 계약](../api/workout-sessions.md)의 V12 START·조회·takeover, V13 snapshot·승인 요청/해결, V14 FINISH·최초 평가·AUTO_CLOSED, V15 종료 후 정정·명시 복구·논리 삭제·현재 평가·승인 해결이다.
수행 누락은 삭제가 아니며, 명시 삭제 ID와 허용 정정의 before/after를 보존한다. 높은 revision도 삭제 UUID를 자동 복구하지 않는다. 완료 수행이 있는 종목 제외는 먼저/동시에 해당 수행 전부를 명시 삭제해야 한다. 최초 계획은 줄이지 않는다.
승인 요청/처리 결과는 후속 snapshot에서 누락되어도 보존한다. KEEP_CURRENT의 NOT_APPLIED/해결 시각은 세션 재조회로 확인하며 영구 요청 영수증을 추가하지 않는다. 출처 없는 신규 종목은 수행 저장을 허용하지만 루틴 승인으로 적용하지 않는다.
Frontend·IndexedDB 연결은 후속 단계로 미구현이다. 최초 평가와 현재 평가를 혼동하지 않으며 AUTO_CLOSED에는 명시 종료 평가를 생성하지 않는다.
개인 로컬 V11 적용·기존 데이터 보존은 사용자 확인 사항이며 V12~V15는 개인 로컬에 적용하지 않는다.

이 문서는 **Task 009의 새로운 구현 기준**이다. 기존 `task-009-0-write-domain-api-design-v0.1.md`, `v0.2.md`의 `WorkoutCommand`·필드별 의도 비교·범용 충돌 해결·명령 영수증/변경 feed 계획을 **현재 구현 요구사항으로 사용하지 않는다**. 과거 문서와 현재 정책이 충돌하면 이 문서를 우선한다. 단, 기존 Task 006에서 확정된 **운동 도메인 사실과 평가 정책**은 이 문서에서 명시적으로 바꾸지 않은 이상 유지한다.

**결정문:** Overload는 온라인 중심 서비스이다. 새 운동 시작, 종목·루틴·설정 관리, 계정·로그아웃 등은 온라인 기능이다. **오프라인 및 iPhone PWA 백그라운드 대응은 이미 시작한 운동의 데이터 보호와 복원에만 적용한다.** 각 사용자는 진행 중인 운동을 하나만 보유하고, 한 번에 한 기기만 편집한다. 프론트엔드는 진행 운동의 전체 로컬 상태를 IndexedDB에 보존한다. 서버에는 **세트/유산소 완료, 운동 종료, 재연결** 시점에 **중간 변경 이력이 아닌 최종 확정된 운동 스냅샷**을 보낸다. 서버는 계정·편집 권한·순번을 확인하고 PostgreSQL 트랜잭션으로 저장한다. Redis, 범용 Command, 범용 Outbox, 필드 병합, 충돌 해결 엔진은 도입하지 않는다.

## 2. 범위와 비범위

### 2.1 포함

- 온라인 운동 시작과 현재 진행 운동 조회.
- IndexedDB 로컬 진행 상태, 미완료 세트 초안, 타이머 복원.
- 완료 세트·유산소 결과를 포함한 운동 **전체 확정 스냅샷** 동기화.
- 편집 기기 이전, 이전 권한 차단, revision 기반 중복/역전 방지.
- 온라인 명시 종료 및 네트워크 단절 시 종료 의도 로컬 보관.
- **24시간 서버 미갱신** 운동 자동 종료와 마지막 서버 확정 실적 보존.
- 자동 종료된 기록 포함, 완료 이력의 온라인 정정·삭제.
- 종목·루틴·운동 설정의 **일반적인 온라인 API**.
- 기존 운동 계획·수행·승인 중량·평가 규칙 보존.
- Backend·Frontend·테스트·현행 문서의 불필요한 구조 감사 및 제거.

### 2.2 명시적으로 제외

- 새 운동의 오프라인 시작.
- 종목·루틴·설정·계정·로그아웃의 오프라인 변경 대기열.
- 다중 기기 동시 편집, 동시 오프라인 수정의 자동 병합/수동 충돌 해결 UI.
- 필드별 발생 시각 승자 판정, `IntentStamp`, `fieldBases`, `RESOLVE_WRITE_CONFLICT`.
- 명령별 영구 영수증, 범용 `sync_operations`, 범용 변경 feed 및 pull cursor를 이번 쓰기 설계의 필수 구조로 두는 것.
- Redis 또는 별도의 임시 저장소, timer tick/주기적 서버 heartbeat.
- 현재 기능과 직접 무관한 미래 확장 인터페이스·범용 엔진.

## 3. 도메인 불변 규칙: 저장 방식 변경과 구별

다음은 **동기화 구조 간소화로 삭제하면 안 되는 제품 동작**이다.

1. **InitialPlan**: 운동 시작 시 계획 원본이며 시작 후 불변. 당시 루틴·종목 이름과 기준 수치·순서·출처를 보존한다.
2. **AppliedPlan**: 진행 중 사용자가 실제 적용한 계획. 최초 명시 종료 시 봉인하며, 종료 후 새 종목/계획/목표/순서 편집은 허용하지 않는다.
3. **실제 수행**: `performedSets`의 **사용자가 완료한 세트만** 공식 실적으로 취급한다. 빈 예정 슬롯 또는 입력 중 초안을 실적에 포함하지 않는다. 예정 세트보다 추가로 수행한 세트도 저장한다.
4. **승인 중량**: 최초 기준·명시 승인된 중량·오늘만 임시 중량을 구별한다. 승인 사건 및 당시 승인 근거는 실제 운동 문맥과 함께 보존한다. 자동 승인/증량/감량 금지.
5. **점진적 과부하 평가**: 원계획 대상 종목의 목표 N개 기준으로, 현재 삭제되지 않은 유효 수행의 **ordinal/ID 순 첫 N개**를 결정적으로 선택한다. N개 이후 추가 수행 자체로 자격을 박탈하지 않는다. 비교 기준은 **한 번의 비교 가능한 과거 세션**이며 여러 세션의 최고 세트를 합성하지 않는다.
6. **종료 당시 평가**: 명시 종료 시점의 `completionAssessment`는 보존하고, 사후 정정 시에는 현재 평가를 재계산한다. 원래 평가·봉인 계획·승인 사건을 소급 변조하지 않는다.
7. **유산소**: 타이머 원본과 정정된 실적을 구분한다. 실제 유산소 완료/건너뜀 상태를 구별하며, 매초 네트워크 호출을 하지 않는다.
8. **실제 운동 시각**: 프론트에서 발생한 세트 수행/승인/시작/종료 시각을 사실로 보관한다. 운동 날짜는 시작 당시 사용자 현지 날짜와 IANA 시간대를 보존하며 재연결·서버 저장 시각으로 바꾸지 않는다.
9. **정정·삭제**: 종료 후에도 허용된 수행 정정·개별 세트/세션 삭제를 지원하고, 변경 전후 사실 또는 필요한 감사 정보를 기존 도메인 규칙대로 보존한다.
10. **소유권·계정·세대**: 다른 계정의 자원 참조를 허용하지 않고 기존 `dataGeneration`, 계정 삭제/초기화의 경계를 유지한다. 숫자는 정확한 decimal/정수 검증으로 처리한다.

> 중요: 위 **승인 사건·수행 정정의 도메인 기록**은 삭제 대상인 `WorkoutCommand`의 **네트워크 명령별 영수증**과 다르다. 중간 API 요청을 영구 저장하지 않더라도 제품상 불변이어야 하는 사건과 역사 정보는 보존해야 한다.

## 4. 세션 상태 모델

### 4.1 권장 상태

- `ACTIVE`: 사용자가 온라인에서 시작했고 계속 기록할 수 있는 세션.
- `FINISHED`: 사용자가 **운동 종료를 명시**하여 확정된 세션.
- `AUTO_CLOSED`: 마지막 서버 유효 갱신 이후 24시간이 지나 **서버가 마지막으로 가진 완료 데이터만 보존하고 자동 종료**한 세션.
- `DELETED`: 사용자 요청에 따른 논리적 삭제 또는 기존 삭제 정책과 정합적인 상태. 실제 테이블에서는 `deleted_at`으로 표현 가능.

`AUTO_CLOSED`는 사용자가 운동 전체를 정상 완료했다는 뜻이 아니다. **기록의 보존 및 진행 상태 해제**를 의미한다. `FINISHED`의 사용자 명시 종료와 동일시하거나 자동으로 전체 목표 달성을 표시해서는 안 된다. 자동 종료된 세션은 완료/과거 기록 화면에서 **자동 종료·부분 기록**으로 표시하고, 이후 허용된 온라인 정정·삭제를 지원한다.

### 4.2 한 사용자당 ACTIVE 하나

- 온라인 `START`는 계정 현재 세대의 ACTIVE를 먼저 확인한다.
- DB의 `UNIQUE (user_id) WHERE status='ACTIVE'` 부분 유일 인덱스로 세대와 무관하게 경쟁 시작을 최종 방어한다.
- 새로운 START 시 기존 ACTIVE가 24시간 만료 상태라면 **같은 트랜잭션에서** 기존 운동을 `AUTO_CLOSED`로 전환한 후 새 운동을 생성할 수 있다.
- 기존 세션의 다른 브라우저 접속은 새 운동을 만들지 않고 기존 ACTIVE를 조회하도록 유도한다.

### 4.3 24시간 판정

- 기준은 서버의 `last_workout_synced_at`으로 한다. 운동 시작과 **실제 확정 운동 상태가 달라진 성공 저장**에서만 갱신한다. 명시적 편집 권한 이전은 갱신하지 않는다.
- 단순 조회, 타이머 tick, 실패한 쓰기, 동일 revision 재전송은 24시간 기한을 연장하지 않는다.
- `now >= last_workout_synced_at + 24 hours`이면 다음 상태 전이 시 또는 간단한 예약 정리 작업에서 `AUTO_CLOSED` 처리한다.
- 자동 종료는 서버에서 **그때 이미 확정된 완료 세트**와 완료 유산소 결과를 보존한다. 예: A 운동 3세트 + B 운동 2세트 저장 뒤 24시간 미갱신 ⇒ 그 **5세트 그대로** 과거 기록에 남음. 입력 중 초안이나 서버에 오지 않은 6번째 세트를 임의로 추가하지 않는다.
- 자동 종료 시각(`auto_closed_at`)과 실제 마지막 수행 시각을 구별한다. 운동 종료 시각·운동 시간·활동 시간을 **만료 시각으로 임의 확장하지 않는다**.
- 명시 종료 때의 `completionAssessment`가 존재하지 않는 자동 종료 세션에는 허위의 '사용자 명시 완료 평가'를 생성하지 않는다. 과거 기록의 현재 평가를 표시해야 한다면 해당 상태임을 분명하게 구별한다.

## 5. 편집 기기 소유권

### 5.1 최소 상태

| 필드 | 의미 |
|---|---|
| `sessionId` | 진행 운동 UUID. 여러 기기에서 같은 세션을 조회한다. |
| `editorDeviceId` | 현재 편집 브라우저/설치 인스턴스를 구별하는 로컬 UUID. **인증 수단 아님**. |
| `writerEpoch` | 편집 권한을 인수할 때 서버에서 단조 증가시키는 정수. |
| `revision` | **현재 epoch의** 최종 확정 스냅샷 순번. |
| `lastWorkoutSyncedAt` | 24시간 자동 종료 판정의 서버 기준 시각. |

### 5.2 이전 절차

1. PC 또는 휴대폰은 기존 로그인으로 현재 진행 운동을 조회한다. 권한이 없으면 조회만 가능하다.
2. 사용자가 명시적으로 **'편집 권한 가져오기'**를 선택하면 서버에서 사용자·세션 상태를 확인한다.
3. 세션 행을 잠그고 `editorDeviceId`를 요청 기기로, `writerEpoch`를 `+1`로 변경한다. 새 epoch의 revision 기준은 **0으로 시작**하도록 명시적으로 초기화한다. 이때 기존 세트 데이터는 유지한다.
4. 서버가 **자신이 가진 최신 확정 운동 상태와 새 epoch**를 새 기기에 반환한다. 새 기기는 그 상태를 로컬 기준점으로 삼는다.
5. 이전 기기는 오프라인 여부와 관계없이 승인할 필요가 없다. 기존 epoch의 후속 요청은 서버에서 거절한다.

이전 기기의 미전송 로컬 데이터는 새 기기에 자동으로 합치지 않는다. 권한 인수 시 사용자에게 짧게 안내한다. 같은 기기가 다시 편집하려면 다시 명시적으로 권한을 가져올 수 있다. `deviceId`는 복제될 수 있으므로 기존 **인증·세션·CSRF·계정 범위** 검증을 생략하는 근거로 사용하지 않는다.

## 6. Frontend 데이터 계약 및 동기화

### 6.1 로컬 IndexedDB의 역할

**하나의 현재 운동을 다시 열어 이어서 할 수 있을 만큼만** 저장한다. 계정과 현재 데이터 세대별로 분리하여 다른 계정의 내용을 보여주지 않는다.

- 세션 UUID, 운동 시작 현지 날짜/시간대, 당시 InitialPlan, 현재 AppliedPlan.
- 완료 세트와 완료 유산소 결과, 실제 사용자 입력/수행 시각, 승인 중량 사건·근거 등 최종 사실.
- 입력 중 미완료 세트의 텍스트 초안, 화면상 선택/작업 중량, 휴식·유산소 타이머 기준 앵커.
- `editorDeviceId`, `writerEpoch`, 다음 로컬 revision, 서버에서 마지막으로 확인한 revision과 필요 최소한의 동기화 상태.
- 오프라인 중 사용자가 누른 **운동 종료 의도와 그 시각**. 네트워크 복구 전 서버에서 종료가 성공했다고 표시하지 않는다.

화면 잠금·백그라운드 진입 때에만 저장하는 방식은 금지한다. **입력 내용이 바뀔 때 미리 로컬 저장**하고 완료 버튼과 같은 중요한 상태 전이는 IndexedDB 트랜잭션 완료를 확인한다. 저장 실패를 저장 성공으로 표시하지 않는다. Safari/PWA의 로컬 저장소는 OS 설정·공간 부족·앱 삭제 등에 의해 유실될 수 있으므로 절대적 영구 보존은 약속하지 않는다.

### 6.2 전체 로컬 상태와 서버 송신 상태의 차이

- **LocalWorkoutState** = 화면 복원에 필요한 **완료 사실 + 미완료 입력 초안 + 타이머 앵커 + 동기화 메타**.
- **ServerWorkoutSnapshot** = 그 시점까지 **최종 확정한 계획 변경·완료 세트·승인 사건·완료 유산소 실적**을 포함한 운동 세션의 **전체 확정 상태**.
- 미완료 입력 초안은 서버의 **공식 완료 세트**로 보내지 않는다. 어떤 세트가 완결됐는지 boolean/상태와 실제 완료 시각으로 명확히 구분한다.
- 여러 번 추가·수정·삭제한 중간 요청을 전부 보내지 않는다. 예: 60kg 입력→65kg 정정→2세트 추가→2세트 삭제→3세트 완료 ⇒ **최종 스냅샷 한 번** 전송.
- 원본 사실이어야 하는 `InitialPlan`, 봉인된 평가, 명시 승인 사건은 전체 스냅샷이라는 이유로 임의 삭제·재작성하지 않는다. 서버가 검증한다.

### 6.3 서버 전송 트리거

| 트리거 | 서버 동작 |
|---|---|
| 웨이트 **세트 완료** | 해당 완료 세트까지 포함한 최신 확정 스냅샷 전송 |
| 유산소 **완료** | 최신 확정 스냅샷 전송 |
| 사용자 **운동 종료** | 최종 스냅샷 + 종료 의도 **한 요청**으로 원자 처리 |
| 온라인 **재연결 / 앱 재개 후 미동기화 발견** | 현재 편집 권한/세션 상태를 조회하고, 유효하면 최신 확정 스냅샷 전송 |
| 입력 중인 중량·횟수 편집 | **IndexedDB만 갱신**, 네트워크 요청 없음 |
| 세트 추가·수정·삭제 | 로컬 갱신. **다음 완료/종료/재연결**에 함께 반영 |
| 타이머 매초 tick·화면 이동 | 서버 전송 없음. 시간 앵커만 필요한 때 로컬 저장 |

2초 디바운스 서버 송신, 주기적 동기화 또는 네트워크 heartbeat는 도입하지 않는다. 20세트를 운동 중 완료하고 별도 변경이 없다면, 일반적으로 세트 완료 동기화는 약 20회다(시작·종료 별도). 화면이 백그라운드로 갔다고 송신 성공을 보장하지 않으며, 재개 후 재시도한다.

### 6.4 전송 순서와 revision

- 하나의 편집 권한 epoch에서 서버 전송을 **동시에 한 요청만** 실행한다.
- 서버 송신 대상에 의미 있는 확정 상태 변경이 생길 때 로컬 `revision`을 단조 증가시킨다. **미완료 초안의 키 입력만으로 서버 revision을 늘릴 필요는 없다.**
- 이미 요청이 전송 중일 때 추가 세트가 완료되면 과거 버전들을 큐에 모두 넣지 않는다. 진행 중 요청이 끝나면 최신 상태 **한 번**을 다시 보낸다.
- 네트워크 실패 시 IndexedDB 최신 상태를 유지한다. 요청이 서버에서 성공했으나 응답이 유실되더라도 같은 epoch/revision/내용으로 안전하게 재시도한다.
- ACK가 돌아왔을 때 **서버 확정 revision**만 갱신하고, 그사이 변경된 로컬 최신 상태를 이전 스냅샷으로 덮지 않는다.
- 타이머는 매초 DB에 쓰지 않고 `startedAt`, `pausedAt`, `endAt`, `accumulatedMs` 등의 기준값으로 복원한다. 앱 백그라운드에서 JS가 지속 실행되는 것을 전제하지 않는다.

## 7. 서버 Snapshot·revision 처리 규칙

### 7.1 저장 요청의 최소 의미

```json
{
  "writerEpoch": 2,
  "revision": 15,
  "snapshot": {
    "sessionId": "<UUID>",
    "initialPlan": "<시작 시 확정한 불변 계획의 참조/원본>",
    "appliedPlan": "<현재 적용 계획>",
    "performedSets": "<현재 유효 완료 세트 목록>",
    "cardioActivities": "<확정한 유산소 상태/결과>",
    "approvalEvents": "<변경 불가능한 승인 사실>"
  }
}
```

위 JSON은 **계약의 구조 예시**이며 문자열 플레이스홀더는 실제 API의 타입 스키마가 아니다. 정확한 세부 DTO는 기존 Task 006 도메인 모델과 Task 008 현재 Entity에 맞춰 작성한다. `sessionId`는 URL과 body가 불일치하면 거절한다. 전체 확정 스냅샷에서 삭제된 현재 유효 세트는 서버의 해당 세트 삭제/정정 규칙에 따라 처리하고, 필요하다면 삭제 사건을 도메인 기록으로 남긴다.

### 7.2 서버 판단 표

| 요청 조건 | 처리 |
|---|---|
| 본인 세션, ACTIVE, 현재 `writerEpoch`, 높은 `revision` | 입력 및 도메인 불변식 검증 후 **하나의 DB tx에서** 현재 확정 스냅샷 반영 |
| 같은 epoch/revision/실질 동일 내용 | **중복 ACK 성공**, 세트/승인 사건 재생성 없음, 24시간 시각 갱신 없음 |
| 같은 epoch/revision/다른 내용 | **거절** (`REVISION_PAYLOAD_MISMATCH`) |
| 현재 epoch의 더 낮은 revision | **오래된 요청 거절 또는 STALE 결과**. 서버 확정 상태 유지 |
| 이전 epoch에서 도착한 요청 | **거절** (`EDITOR_OWNERSHIP_LOST`). 서버 확정 상태 유지 |
| 세션이 FINISHED/AUTO_CLOSED/DELETED | 진행 스냅샷 저장 **거절**. 자동 병합·자동 재개 없음 |
| 다른 계정의 세션·리소스 | 기존 보안 정책에 따라 존재 정보를 노출하지 않고 차단 |

**동등 revision의 내용 판별:** 현재 epoch에서 마지막으로 확정한 스냅샷에 한하여, 서버의 정규화된 타입 DTO를 기반으로 **의미가 안정적인 단일 hash** 또는 현재 저장 상태의 동등성 검사만 사용한다. 이는 **한 세션의 마지막 중복 요청 검사**이지 기존 `WorkoutCommandCodec`·RFC JCS·명령 영수증 체계를 재도입하는 것이 아니다. 숫자·순서·UUID 정규화 규칙이 불안정하면 hash 대신 스냅샷의 의미상 동등성을 검사하도록 구현한다.

### 7.3 DB 원자성

- 서버 트랜잭션에서 사용자 소유·세대 확인 → `workout_sessions` 대상 행 잠금 → 상태·epoch·revision 검사 → 도메인 검증 → 실제 세트·계획·유산소·승인 사실 및 세션 메타 반영을 **한 번에 커밋**한다.
- 로컬과 서버의 세트 ID는 안정적인 UUID로 식별한다. ordinal만으로 수행을 추측해 병합하지 않는다. 각 계정·세션·종목의 FK/유일성·범위를 검증한다.
- 기존 도메인의 불변 원본(InitialPlan, 과거 승인, 최초 명시 종료 평가) 훼손을 허용하지 않는다.
- **만료 검사는 `snapshot`과 `finish` 수신 시에도 반드시 수행한다.** 스케줄러가 아직 실행되지 않았더라도 마지막 서버 갱신 이후 이미 24시간이 지났으면, 해당 세션을 같은 행 잠금 아래 `AUTO_CLOSED`로 확정하고 뒤늦게 도착한 ACTIVE 변경을 적용하지 않는다.
- 저장 실패 시 **부분 수행·부분 삭제·부분 승인**이 남지 않도록 전체 롤백한다.
- Redis, 독립 receipt 트랜잭션, 서버 네트워크 작업 대기 중 락 유지, 변경 feed를 사용하지 않는다.

## 8. 최소 Backend API 제안

기존 인증 쿠키·CSRF·`X-Request-ID`·오류 응답 규칙을 사용한다. 아래는 **구현 시 계약으로 확정할 권장 경로**다. 실제 API 중복 여부는 코드 감사에서 검증한다.

| Method | 경로 | 책임 |
|---|---|---|
| `POST` | `/api/v1/workout-sessions` | 온라인 START, 초기 계획·세션 및 편집 기기 생성 |
| `GET` | `/api/v1/workout-sessions/active` | 본인 ACTIVE 상태 및 편집 가능 여부 조회 |
| `GET` | `/api/v1/workout-sessions/{sessionId}` | 본인 세션·기록 조회(기존 Task 008 R 계약과 조화) |
| `POST` | `/api/v1/workout-sessions/{sessionId}/takeover` | 사용자 명시 편집 권한 이전, 새 epoch·서버 기준 스냅샷 반환 |
| `PUT` | `/api/v1/workout-sessions/{sessionId}/snapshot` | 현재 epoch/revision의 **전체 확정 상태** 저장 |
| `POST` | `/api/v1/workout-sessions/{sessionId}/finish` | 최종 스냅샷 검증/저장 + 명시 종료를 **한 트랜잭션**에서 수행 |
| `PATCH` 또는 명시 엔드포인트 | `/api/v1/workout-sessions/{sessionId}/records/...` | 종료된 운동의 **허용된** 수행 정정·삭제. 일반 온라인 API, 승인 이력/불변 계획 보존 |
| 일반 `POST/PATCH/DELETE` | `/api/v1/exercises`, `/api/v1/routines`, `/api/v1/workout-settings` 등 | 온라인 종목·루틴·설정 관리, 각 도메인 Service로 검증/저장 |

### 8.1 요청/응답 핵심

- 운동 시작 요청은 기존 인증 사용자의 현재 세대 및 시작 루틴 계획을 검증한다. **오프라인 START 불가**.
- 진행 스냅샷 성공 응답은 `sessionId, writerEpoch, acceptedRevision, serverCommittedAt`와 필요 시 현재 상태를 반환한다.
- 에러는 기존 공통 HTTP 계약을 존중한다. 의미별 `SESSION_NOT_ACTIVE`, `EDITOR_OWNERSHIP_LOST`, `REVISION_STALE`, `REVISION_PAYLOAD_MISMATCH`, `VALIDATION_FAILED` 등을 해당 범위에서만 정의한다. 구체적인 HTTP 상태는 기존 008 오류 규칙에 정합적으로 매핑한다.
- `finish`는 **마지막 변경을 포함한 최신 스냅샷과 사용자가 누른 종료 시각**을 한 번에 보낸다. 사전 snapshot 요청 ACK를 기다린 뒤 별도로 종료해야만 하는 구조는 만들지 않는다.
- 응답 유실 뒤 동일한 명시 종료를 재시도할 경우, 같은 세션·epoch·revision·최종 내용의 이미 확정된 종료라면 **그 종료 결과를 재응답**하고 새 세션/기록을 중복 생성하지 않는다. 다른 내용의 종료나 폐기 상태에서의 새 요청은 거절한다.
- 편집 권한 이전은 이전 기기의 승인 없이 처리하되, **서버가 기존의 미전송 로컬 변경까지 가지고 있다는 인상을 주지 않는다**.

## 9. PostgreSQL·Flyway 설계

### 9.1 서버 원본

- **PostgreSQL이 단일 서버 원본**이다. 별도 Redis 캐시/영속화 저장소를 필수 경로에 두지 않는다.
- `workout_sessions`가 소유자·세대·상태·시작/종료·최근 서버 갱신·편집 기기·epoch·현재 revision을 소유한다.
- 운동 계획·실제 완료 세트·유산소 결과·승인 사건은 기존 Task 006/008의 **관계형 원본 + 적절한 불변 계획 스냅샷** 경계를 따른다. 최초 계획과 승인 사건, 최초 명시 종료 판단은 별도 불변 사실로 둔다.
- **진행 운동도 PostgreSQL에서 바로 실제 확정 세트를 저장**한다. 종료 시 Redis나 다른 DB에서 복사할 필요가 없다. 종료는 스냅샷 최종 반영 후 세션 상태 변경 및 평가 확정이다.
- 완료된 실적의 고유 원본이 `performed_sets`라면 별도 가변 JSON에 실적을 중복 저장하지 않는다. 동등 revision의 중복 확인에는 마지막 확정 payload의 작은 hash 같은 메타만 필요할 수 있다.

### 9.2 핵심 제약·인덱스 후보

- `dataGeneration`과 무관한 사용자별 ACTIVE 세션 부분 UNIQUE.
- 세션 ID 및 자식 수행의 owner·generation·session FK.
- 유효 수행 세트 `(session_exercise_id, ordinal)`의 중복 방지 제약(삭제/tombstone 처리와 양립).
- `writerEpoch >= 0`, `revision >= 0`, 정확한 `NUMERIC` 중량 및 reps 양수 등 유효성.
- `AUTO_CLOSED`가 명시 `FINISHED`인 것처럼 기록되지 않도록 종료 사유 또는 구분된 상태 저장.
- 복합 DB/JPA/JDBC 트랜잭션은 기존 Task 008에 검증된 `workoutTransactionManager` 및 혼합 저장 경계를 따른다.

### 9.3 V9 정리 정책

기존 009-1A에서 `V9__add_workout_write_foundation.sql`에 추가했다고 보고된 항목은 `exercise_definitions.version/deleted_at/intent_stamps`, `user_workout_settings.version/intent_stamps`, `workout_sync_state`, `sync_operations`, `workout_change_batches`이다.

- **이미 적용된 Flyway 파일은 수정·삭제하지 않는다.** 이는 구 설계를 유지하려는 예외가 아니라 마이그레이션 이력 체크섬 및 환경 간 일관성을 위한 규칙이다.
- 새 구조에서 쓰지 않을 `intent_stamps`, `sync_operations`, `workout_change_batches`, `workout_sync_state`는 실제 참조·데이터·FK를 감사한 후 **신규 번호의 마이그레이션으로 실 DB에서 제거**한다.
- `version`이나 `deleted_at`은 일반 온라인 수정·논리 삭제에 여전히 유용할 수 있으므로 실 사용 여부를 판별해 유지/제거한다. 모든 V9 필드를 일괄 삭제하지 않는다.
- 기존 PostgreSQL에 사용자 실데이터가 있다면 데이터 보존, 적용 순서, 롤백/복구 방법을 먼저 확인한다. **Flyway checksum을 맞추려고 이력을 지우거나 DB를 초기화하지 않는다.**

## 10. 24시간 자동 종료 구현

**최소 설계:** PostgreSQL 상태 판정 + 간단한 서버 예약 정리, 그리고 **START/GET/TAKEOVER/SNAPSHOT/FINISH** 경로에서 만료 조건 재확인.

1. 서버는 `last_workout_synced_at`이 24시간 이전이고 `ACTIVE`인 세션을 찾는다.
2. 해당 세션 행을 잠그고 **잠금 후 다시** 최신 상태/갱신 시각을 확인한다. 새 완료 세트 저장과 자동 종료가 경합하면 **먼저 DB에 확정된 트랜잭션**이 기준이 된다.
3. 만료 조건이 유지되면 현재 PostgreSQL에 저장된 완료 수행만 가지고 `AUTO_CLOSED`로 전환한다. 원계획의 미완료 세트를 자동 완료하지 않는다.
4. 자동 종료 메타/현재 평가 구분을 저장하고 ACTIVE 슬롯을 해제한다.
5. 사용자가 다시 열면 과거 기록으로 조회·허용 범위 내 정정·삭제할 수 있다. **늦게 도착한 과거 ACTIVE 스냅샷은 거절**한다.

**예약 작업은 정확히 24시간 0초에 실행될 필요는 없다.** 조건 검사로 24시간 이상 지난 ACTIVE를 새 운동 시작 전에 반드시 정리한다. 정리 주기는 운영 단순성에 맞춰 선택하되, 자동 종료 시각을 실제 운동 수행 시각으로 쓰지 않는다.

## 11. 프론트 복원과 24시간 종료의 경계

- IndexedDB의 저장된 로컬 세션이 서버의 현재 `ACTIVE`이고 epoch가 같으면, **그 기기의 최신 확정 상태**를 순서대로 동기화한다.
- 서버가 이미 `AUTO_CLOSED`라면 서버 최종 기록이 공식 원본이다. 기기에만 남은 더 최근 오프라인 세트를 **자동 병합·자동 덮어쓰기하지 않는다**.
- 이전 epoch라면 다른 기기가 권한을 인수한 것이다. 자동 재전송하지 않고 현재 서버 상태를 표시한다.
- 이때 미전송 로컬 원본을 다른 계정에 노출하거나, 서버가 반영했다고 속여서는 안 된다. 사용자에게 서버에 남은 기록을 표시하고 **허용된 온라인 수동 정정 경로**를 안내한다. 일회성 로컬 복구 화면을 위해 범용 충돌 관리 시스템을 만들 필요는 없다.
- 인터넷 없이 앱을 다시 열 수 있는 상태에서는 **기존 로컬 진행 운동에 한해** 기록을 이어갈 수 있다. 새 운동 및 일반 관리 기능은 온라인 복구 후 사용한다.
- 온라인 명시 로그아웃/계정 전환 시 로컬 계정 데이터의 접근 범위를 분리한다. 미동기화 데이터가 남았다면 그 사실을 안내하되, 로그아웃 자체의 오프라인 지원 시스템은 만들지 않는다.

## 12. `WorkoutCommand` 및 과설계 제거 원칙

### 12.1 새 구조에서 제거 대상

기존 1A/1B 보고서에 나타난 **교체·삭제 후보**(최종 삭제 대상은 실제 정적/동적 참조 감사 후 확정):

- 패키지 `workoutcommand`의 공통 명령 dispatcher/controller/service/store 및 공통 명령 응답·오류 계층.
- `CommandEnvelope`, `CommandJson`, `WorkoutCommandCodec`, 명령별 canonical fingerprint, `IntentStamp`, `fieldBases`, `RESOLVE_WRITE_CONFLICT`, 명령 복구/충돌 비교 기능.
- `/api/v1/workout-commands`, `/api/v1/workout-operations/{operationId}`, fieldBase/stamp 전용 edit-context API와 그 호출부.
- 범용 최종 receipt·feed에만 필요한 코드, 테이블 접근, 문서 참조, 테스트.
- 더 이상 호출되지 않는 DTO·enum·mapper·adapter·미래 추상화와 중복 검증 코드.
- 구형 동기화 계약만 확인하는 통합 테스트/fixture. **동일한 보안·트랜잭션 성질을 검증하는 테스트는 새 API로 이전**.

### 12.2 활용 여부를 선별할 대상

- `Counter`, `WeightKg`, `WorkoutWriteGuard`의 정확한 숫자 검증·인증 계정 범위·DB 트랜잭션 경계 같은 **기능**은 필요하다. 하지만 기존 클래스/패키지를 보존할 의무는 없다. 새 도메인에 맞는 가장 단순한 위치/형태로 옮기거나 직접 대체할 수 있다.
- 기존 인증·Google/이메일 로그인·Spring Session·CSRF·Request ID, Task 008 조회 API, 정상 계정 seed와 DB 거래 설정은 **기능 유지**가 원칙. 불필요한 재개발 금지.
- 기존 제품 정책·사후 정정·승인 이력을 위한 **실제 도메인 데이터**는 명령 영수증 제거와 별개로 유지한다.

### 12.3 코드 정리의 완료 정의

- 프로젝트를 새로 읽는 개발자가 **현행 설계 한 문서와 해당 기능의 Controller/Service/Repository**를 따라가면 이해할 수 있어야 한다.
- '언젠가 필요할 수 있다'는 이유로 구현하지 않는 generic engine이나 미사용 API·호환 wrapper·shadow package를 남기지 않는다.
- 구 설계 문서는 현재 개발 경로에서 제거한다. 이전 문서가 필요하면 Git 이력에서 확인한다. **프로젝트 내부에 별도 유산 문서 폴더를 만들어 현재 기준을 혼동시키지 않는다.**
- `README.md`, `AGENTS.md`, 개발 가이드, 프로젝트 구조도에서 옛 Task 009 문서/명령 API로 향하는 링크 및 지시문을 정리한다.
- 단, 이미 적용된 Flyway 과거 마이그레이션은 **DB 이력 보존 예외**로 남긴다.

## 13. 수정 전 필수 코드 감사 절차

**현재 실제 작업 공간에 대한 감사가 선행**되어야 하며 문서에 적힌 과거 Git 상태를 현재 사실로 가정하지 않는다.

1. Backend/Frontend 각각 현재 브랜치·HEAD·staged/unstaged/untracked 상태를 기록한다. 사용자 작업/미커밋 내용이 섞여 있는지 확인한다.
2. 실제 009-1A/1B 파일 목록과 전역 참조를 검사한다. Controller route, FE 호출, DB migration, Entity, test fixture, Gradle/JPA scan 등 의존 관계를 파악한다.
3. 현행 기능을 유지/교체/제거/신규 추가로 분류하고 **각 제거의 근거와 회귀 영향**을 기록한다.
4. 불필요한 구현을 더 이상 참조하지 않도록 API 경계를 바꾸고, 테스트로 확인한 뒤 코드·클래스·문서 링크를 실제로 삭제한다.
5. DB 제거는 신규 Flyway migration을 작성한다. 적용 전 새 DB와 기존 V9 적용 DB 모두에서 업그레이드 경로를 검증한다.
6. 설계에 어긋나는 코드를 '기존 테스트가 통과했으므로' 보존하지 않는다. 단, 인증·데이터 무결성을 손상시키는 무차별 Git reset/clean/DB drop 명령도 쓰지 않는다.

| 단계 | 범위 | 완료 조건 |

한 번에 모든 파일을 재작성하지 않는다. **각 단계는 작은 검증 가능한 변경으로 분리**하되, 불필요한 구형 구조를 최종 코드에 남기지 않는다. 인증·조회 등 범위 밖 정상 기능을 훼손하지 않는다.

## 16. 구현 시 해석 기준과 비결정 사항

**이 문서에서 확정한 것은 제품 동작과 책임 경계**다. 다음 세부 사항은 실제 코드/DB 감사와 DTO 설계에서 **가장 단순한 구현**으로 결정하되, 제품 규칙을 바꾸는 데 사용해서는 안 된다.

- 세션 내부 최종 DTO의 필드 이름, 물리 테이블 분할, Controller/Service 클래스 이름, 구체적인 HTTP 오류 status.
- 서버가 동등 revision·동등 내용 검사를 수행할 때의 **최소한의** hash 또는 동등 비교 구현.
- 자동 종료 스케줄러의 실행 주기. 24시간 **판정 기준 자체**는 변경할 수 없다.
- Safari/PWA의 저장 용량/복구 테스트 방식. 브라우저의 보장 범위를 넘는 '절대 무손실' 마케팅/기술 주장은 하지 않는다.
- 자동 종료 기록의 `completionAssessment` 부재 또는 별도 자동종료 평가 표현은 기존 도메인 평가 계약에 맞춰 확정한다. **사용자가 명시 종료한 것처럼 허위 원본을 생성하지 않는 규칙은 고정**이다.

설계를 바꾸는 변경이 필요한 경우 해당 지점만 근거와 영향을 설명하고 사용자와 논의한다. 이미 확정된 온라인 중심·전체 스냅샷·24시간 보존·명시 편집권 인수·구 코드 제거 원칙을 재논의 없이 뒤집지 않는다.
