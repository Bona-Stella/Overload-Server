## 1. 판단과 권장안

**현재 구현을 모든 Google 사용자에게 제공할 수 있는 능동 재인증 기능으로 승인하는 것은 보류한다.**
현재 코드는 조건에 맞는 인증 시각을 검사하며 안전하게 거절하지만, 공급자가 그 시각의 새 인증을 수행하도록 만들 수 있는 수단은 아니다.

권장 방향은 다음 세 가지를 함께 적용하는 것이다. 아래는 제안이며 이번에 실행하지 않았다.

1. Google LOGIN과 Google 재인증 활성화를 분리하고, 재인증은 **독립적인 기본 비활성 기능**으로 둔다.
2. 검증기·소유권·세션 교체 구현은 보존하되, Google 경로는 조건부 최근 인증 증거의 수용 기능으로 한정한다.
   Google-only 사용자의 일반적인 민감 작업을 이 경로 하나에 의존시키지 않는다.
3. 3B-3 쓰기 API를 열기 전에 기존 계정의 재인증 수단과 **첫 추가 수단 등록/복구의 신뢰 근거**를 확정한다.
   장기적으로 Overload 자체 패스키를 우선 검토하되, 패스키 추가만으로 기존 계정의 최초 등록 문제가 해결되지는 않는다.

## 2. 공식 지원 범위와 기존 설명의 정정

Google 보안 번들은 추가 클레임에 대해 앱의 **In production**, **Verified**, 보안 설정의 **Session age claims** 활성화를 요구한다.
또한 Google 계정에 대한 재인증 요청을 지원하지 않는다고 명시한다:

> Google does not support Google Account reauth requests.

근거: [Google Security bundle — Setup / Authentication time](https://developers.google.com/identity/siwg/security-bundle).

Google OIDC 참조는 `auth_time`을 실제 사용자 인증 시각, `iat`를 토큰 발급 시각으로 구분한다.
따라서 새 토큰을 얻었다는 사실은 새 Google 인증의 증명이 아니다.
[Google OIDC claim reference](https://developers.google.com/identity/openid-connect/reference).

`claims`의 essential auth_time은 클레임 요청이다. Google OIDC 가이드는 별도 설정 필요성을 명시하며,
문서의 prompt 값은 none/consent/select_account다. 이 값들은 새 인증의 강제를 입증하지 않는다.
[Google OIDC authentication parameters](https://developers.google.com/identity/openid-connect/openid-connect).

**재검토 결론:** `max_age=0`을 보낸다는 사실과 Google이 능동 재인증을 지원한다는 사실을 구분해야 한다.
표준 OIDC에서의 의미를 Google의 동작 보장으로 적용할 수 없다. essential auth_time과 조합해도 보장되지 않는다.
이전 문서의 “max_age 지원 미확인 / LIVE 필요”만으로는 부족했고, **요청으로 새 인증을 강제할 수 없다는 제공자 제약**을 명시해야 한다.
단순 Console 콜백 등록이나 LIVE 성공 사례 하나로 이 제약이 해소되는 것도 아니다.

## 3. 현재 조건이 기존 Google 세션에서 충족 가능한가

현재 `GoogleAuthenticationTime.java:31~43`은 다음 조건을 사용한다:

```text
R = 재인증 요청 시작 시각
G = 서명 검증된 Google auth_time
N = 서버 현재 시각

floor_to_seconds(R) <= G <= N + 60초
R <= N < R + 5분
```

일반적인 기존 세션을 가정하면 `G < R`이다. 새 OAuth 요청/콜백/토큰의 시각만 진전하고 G가 유지되는 경우,
현재 검증기는 의도대로 거부한다. 이는 위 공식 구분과 현재 코드에서 도출한 **운영상의 추론**이며 실제 사용자 빈도를 측정한 결과는 아니다.

| 상황 | 현재 조건의 결과와 의미 |
|---|---|
| 오래된 Google 세션에서 OAuth 요청만 다시 수행 | G가 그대로면 거부 |
| 실제 Google 인증이 요청 시작 5분 전 | 제품의 최근 10분 안이어도 현재의 더 엄격한 시작 하한 때문에 거부 |
| 요청 시작 뒤 실제 Google 인증이 발생하고 그 G가 제공됨 | 다른 검증도 통과하면 수용 가능. 앱이 이 사건을 강제할 수 있다는 뜻은 아님 |
| 요청 직전 같은 초에 실제 인증 | 초 단위 내림의 1초 미만 정밀도 허용으로 수용될 수 있음 |
| 새 iat/계정 선택/동의만 발생 | 대체 증거로 수용하지 않음 |
| 클레임 제공 조건을 충족하지 못하거나 G 누락 | 거부 |

“어떤 상황에서도 성공 불가능”은 아니다. 그러나 일반적인 기존 세션에 대해 **사용자가 필요할 때 반복할 수 있는 재인증 절차로 보장할 수 없다.**
새 시크릿 브라우저에서 Google 로그인 후 Overload에 로그인하고 그 다음 재인증을 시작해도, 그 Google 인증이 R보다 앞서면 동일하게 거부된다.
Overload 로그아웃은 Google 세션을 새로 인증시키는 조치가 아니며, Google 전체 로그아웃/브라우저 쿠키 조작을 자동 해결책으로 권장하지 않는다.

기존 일반 Google 로그인 LIVE 성공도 추가 클레임 제공이나 능동 재인증의 검증 결과는 아니다.
현재 개발 클라이언트의 실제 클레임 제공은 미확인이며, 운영 검증을 마쳐도 오래된 G를 자동으로 새롭게 만들 수 있다는 결론은 나오지 않는다.

## 5. Google-only 계정과 3B-3의 순환 의존

Task 006은 인증 수단 연결/해제에 기존 사용자 재인증과 새 수단 소유 증명을 요구하며, 마지막 로그인 수단 제거와 자동 병합을 금지한다.
기존 EMAIL 신원이 없는 Google-only 계정은 3B-1 이메일 REAUTH도 사용할 수 없다.

```text
Google-only + 최근 인증 증거 없음
  → 추가 이메일/패스키를 연결하려면 기존 계정 재인증 필요
  → Google 경로에서 수용 가능한 G를 얻지 못함
  → 연결을 완료할 수 없음
  → 추가 수단을 통한 재인증도 불가능
```

이는 현재 조건과 후속 연결 요구를 조합한 **설계상 교착**이다. 실제 3B-3 쓰기 API는 아직 없으므로 현재 데이터에 발생한 변경 장애라고 주장하지 않는다.
기존에 EMAIL 등 다른 허용 수단이 이미 연결돼 있거나 조건을 충족하는 별도 증명이 있는 사용자는 이 사례와 구분한다.
마지막 Google 로그인 수단의 제거는 최근 인증에 성공해도 별도의 마지막 수단 보호 때문에 허용하면 안 된다.

### 현재 일반 로그인 직후의 10분을 별도로 검토해야 한다

`AuthenticationSessionService.java:35~39`는 새 인증 세션의 `reauthenticatedAt`을 서버 현재 시각으로 초기화한다.
일반 Google LOGIN은 3B-2 전용 auth_time 검증기를 거치지 않는다. `SessionPolicy.java:46~48`은 증명의 종류 없이 이 시각만으로 최근 10분을 판정한다.

따라서 현재 구현상 새 Overload 로그인 직후에는 최근 인증 검사가 true일 수 있다. 이를 이유로
“로그아웃 후 재로그인하면 첫 수단 등록 문제가 안전하게 해결된다”고 판단하면 안 된다.
이는 **새 앱 로그인 증거**와 **최근 실제 Google 인증 증거**를 어떤 작업에 인정할지의 미확정 계약이다.
기존 로그인 구현을 이번에 오류로 단정하거나 변경하지 않았다. 다만 3B-3이 시각 필드 하나를 무조건 신뢰해 이 결정을 우회하지 않도록 해야 한다.

새 이메일 OTP나 새 패스키의 소유 증명만으로 기존 계정 재인증을 대체하면, 탈취한 활성 세션으로 공격자의 수단을 등록할 수 있다.
기존 등록 수단의 재인증과 활성 세션만을 신뢰하지 말라는 원칙은
[OWASP의 인증 수단 변경 지침](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#changing-mfa-factors)과도 부합한다.

최근 G라는 수동적 신호와 새 능동 인증을 같은 보장으로 표현하지 않는다. 이번에는 시간 조건을 바꾸지 않았다.

### Overload 패스키의 구체적인 역할과 한계

WebAuthn은 RP에 범위가 묶인 공개키 자격증명의 서명과 challenge를 검증하는 체계다.
Overload 재인증에는 `userVerification=required`와 서버 측 UV 확인을 포함하고, 단순 사용자 존재 표시만으로 완료하면 안 된다.
근거: [W3C WebAuthn — 인증 assertion 검증](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

도입 시 필요한 Overload 계약은 다음과 같다:

- 이미 현재 UUID에 등록된 credential의 소유자·서명·RP ID·origin·challenge·UV를 서버에서 검증한다.
- 짧은 수명/일회용 challenge를 현재 계정·세션·재인증 목적에 묶고, 기존 JDBC 교체·CSRF·90일 만료 보존 경로를 공유한다.
- Google 계정에 사용하는 패스키와 Overload RP의 패스키는 구분한다. 같은 기기/자격증명 관리자를 사용한다는 사실만으로 신뢰를 넘기지 않는다.
- 새 패스키 등록은 기존 계정의 허용된 증명 뒤에 사용자 명시적 동의로 수행한다. 새 키 생성 자체를 그 증명으로 순환 사용하지 않는다.
- 패스키를 재인증 전용으로 둘지 로그인 수단으로도 둘지 결정해야 한다. 전용 수단이라면 마지막 Google 로그인 수단을 지워도 된다는 근거가 아니다.

이는 Task 006의 Google+EMAIL MVP 범위를 추가하는 결정이다. 인증 도구/라이브러리·스키마·브라우저 UI·복구 정책 검토가 필요하며,
이번 설계 검토가 도입 승인이나 기존 설계 변경을 뜻하지 않는다.

### 최초 등록과 복구는 별도 문제다

| 계정 상태 | 안전한 진행 방향 |
|---|---|
| 허용된 기존 수단으로 최근 증명 가능 | 그 증명 후 새 수단 소유 증명과 명시적 연결 |
| 신규 계정의 최초 등록 절차 | 계정 생성과 결합된 별도 신뢰 초기화 정책 검토. 새 키의 UV만으로 기존 Google 계정 소유를 증명했다고 하지 않음 |
| 기존 Google-only, 허용 증명/사전 복구 수단 없음 | 자동 연결 보류. 별도 승인된 소유권 복구/신뢰 초기화 설계 없이는 교착을 안전하게 해소할 수 없음 |
| 이미 다른 UUID에 속한 이메일 identity | 충돌 처리. 새 주소 증명이나 패스키를 이유로 옮기거나 병합하지 않음 |

초기 가입/재로그인의 어떤 증명을 최초 등록에 허용할지, 기존 사용자에게 어떤 복구 증거를 요구할지는 사용자의 정책 결정이 필요하다.
이메일 주소 추정·활성 쿠키·관리자의 편의상 우회만을 기존 계정 소유권으로 받아들이는 절차는 제안하지 않는다.
계정 식별과 연결은 issuer/sub 기준 및 명시적 소유 증명을 유지한다.
[OWASP federated account linking](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#secure-federated-account-linking).

## 7. 조건부 기능·기본 비활성화·설계 변경의 적용 순서

현재 `GoogleReauthenticationSecurity`와 `GoogleReauthenticationRequests`는 `GOOGLE_OIDC_ENABLED` 하나에 묶여 있다.
`GoogleOidcSecurity.java:152`도 재인증 구성을 직접 호출한다. **일반 Google 로그인만 켜고 재인증만 끄는 독립 플래그는 없다.**
현재 전역 기본값이 false라는 사실만으로 향후 LOGIN 활성화 시 재인증 노출을 제어할 수 있다고 판단하면 안 된다.

권장 후속 변경(이번에 미수행):

1. 예를 들어 `GOOGLE_REAUTH_ENABLED=false`라는 독립 opt-in을 설계한다.
   일반 LOGIN=true/REAUTH=false로 로그인과 OTP가 정상 동작하고 재인증 경로는 사용할 수 없도록 한다.
   실제 `.env`를 변경하는 대신 구현/설정 예시/안전 기본값을 별도 검토한다.
2. UI·문서에서 강제 새 Google 인증 기능이라는 설명을 제거하고, 지원 조건이 있는 보조 증명 경로로 한정한다.
   진입 중 반복 실패를 계정 연결로 우회하거나 자동 재시도하지 않는다.
3. 현재 검증기·JDBC 회전 코드는 보존하되 사용 가능성의 유일한 근거로 삼지 않는다.
4. 보편적인 민감 작업은 사전에 등록한 허용 수단과 명확한 최근 인증 증거 정책으로 설계한다.

이 권고는 Google 일반 로그인 자체를 폐기하거나 실제 계정·세션을 변경하자는 뜻이 아니다.

## 8. 커밋·3B-3 진행 전 결정 및 검증 목록

### 커밋 판정

현 상태를 “Google 재인증 실사용 완료”로 커밋하는 것은 보류를 권한다.
조건부 기능으로 보존하려면 독립 비활성화와 설명 정정, 해당 회귀 검증을 먼저 완료하고 별도 커밋 승인을 받는 것이 적절하다.
사용자가 실험 코드 보존만 승인하는 경우에도 범위·미지원 사항을 커밋 설명에 명시해야 하며, 운영 활성화 승인으로 해석하지 않는다.

### 3B-3 진입 판정

설계 검토는 진행할 수 있다. 다만 다음 결정을 하지 않은 채 Google-only 사용자의 연결·해제 쓰기를 완성됐다고 할 수 없다:

1. 민감 작업에 인정하는 기존 증명 종류, 실제 인증 시각과 앱 로그인 시각의 관계.
2. Google-only 계정의 첫 EMAIL/패스키 등록과 기존 사용자 복구의 신뢰 초기화 방법.
3. 패스키 도입 여부와 로그인/재인증 역할, 분실/마지막 로그인 수단 보호.
4. 증명을 얻지 못한 계정의 명시적 이용 제한과 복구 안내.

이미 연결된 EMAIL 수단을 가진 사용자만 대상으로 범위를 제한하는 방안은 가능하지만, 이것도 후속 범위 승인 사항이다.
그 제한 구현을 모든 Google-only 계정의 문제가 해결된 것으로 보고하면 안 된다.

### 필요한 후속 소스/테스트 — 이번 검토에는 추가하지 않음

| 후속 작업 | 이유/필수 검증 |
|---|---|
| 독립 feature flag와 설정 의존 분리 | LOGIN on / REAUTH off의 로그인·OTP 보존, 재인증 콜백도 활성화되지 않음, 기본 비활성 |
| 기능 명칭·설명 정정 | mock 성공과 provider 능동 재인증 지원을 구분, 게시/검증/설정과 실제 클레임 제공 분리 |
| 증명 의미/최초 등록 정책의 계약 | 새로운 앱 로그인만으로 Google 실제 최근 인증으로 오인하거나 기존 재인증 게이트를 우회하지 않음 |
| 선택한 자체 수단 구현 | 등록/인증/복구·UV·challenge 재생·다른 UUID·다른 세션·마지막 수단·동시 연결 충돌 |
| 시간 수용 기준을 바꾸는 경우 | 별도 승인 후 실제 G로 10분 경계 검사, 반복 OAuth로 기간 연장 금지, 누락/iat 대체 거부 |
| 전체 회귀 | 기존 검증과 fail-closed·90일·CSRF·계정 분리 유지 |

Google 시간 증명을 사용하는 경로에서 auth_time 누락 성공, iat 대체, 계정 선택만의 승인은 허용하지 않는다.
EMAIL/패스키 대안은 해당 수단을 독립적으로 검증하는 경로이며 누락된 Google 증명의 성공 대체값이 아니다. 모든 경로에서 자동 병합을 금지한다.

## 9. 이번 수행 내역과 보존 확인

이번에 한 작업은 공식 공개 문서 조회, 저장소/소스/기존 보고서 읽기, 이 보고서 작성과 diff 검사다.
234개 통과는 이전 실행 결과이며 이번에 새 테스트·Gradle 빌드·LIVE 검증을 수행한 결과로 표시하지 않는다.

변경은 **이 보고서 1개 신규 추가**뿐이다. 시작 시 있던 미커밋 3B-2 파일 20개는 그대로 보존한다.
기존 기술 문서/검증 보고서를 덮어써 역사적 검증 결과를 바꾸지 않았다. 제안한 플래그·패스키·정책도 구현하지 않았다.
시작 시 20개 파일의 내용과 비교해 모두 동일함을 확인했다. 최종 작업 트리는 기존 20개+이 보고서 1개로 21개 변경이며 스테이징은 0개다.
기존 사용자·세션·DB·Docker·프론트·`.env`를 변경하지 않았다. 실제 Google 인증/Resend 발송, Git staging/Commit/Push 없음.
로컬 서버나 테스트 프로세스를 새로 시작하지 않아 이번 검토에서 정리할 프로세스도 없다.

최종 권고는 **독립 기본 비활성화 후 조건부 증명 기능으로 보존 + Google-only 최초 등록/복구 정책을 먼저 확정**이다.
이 판단을 반영한 후속 구현은 별도 승인 범위이며, 이번에는 설계 검토 결과만 제출한다.
