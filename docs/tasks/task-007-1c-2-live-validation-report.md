## 설정·환경 점검

- 시작 Git: `main`, `766f3a260e2d091d930fc2d519414dbe2b851708`, clean, origin/main과 동일.
- RESEND_API_KEY 존재와 기본 형태, 수정된 RESEND_FROM_EMAIL의 bare 주소 형태를 확인했다. 실제 값은 출력하지 않았다.

  다른 `.env` 내용이 달라지지 않았음을 문자열 비교로 검사했다. 생성한 키는 재실행 때 유지했다.
- 발신 주소 수정은 사용자가 수행했다. 에이전트는 PostgreSQL 접속 정보·기타 비밀키를 변경하지 않았다.

  테스트 서버 프로세스의 `--OTP_EMAIL_ENABLED=true` 인자로만 실메일을 일시 활성화했다.

API 키로 공식 Resend GET /logs를 읽기 전용 조회했으나 401 restricted_api_key였다.
발송 전용 키의 조회 권한 제한이므로 이를 첫 POST 전송 실패 원인으로 단정하지 않았다.
전체 권한 키를 새로 만들거나 기존 권한을 확대하지 않았다.
발신 도메인의 Verified 상태는 사용자가 준비한 사항이며, 실제 송신 수락으로 발송 가능함을 확인했다.
별도 도메인 관리 API로 상태를 재조회했다고 주장하지 않는다.

## 수신·OTP·계정 검증

실메일 요청과 최초 CSRF 취득은 같은 HttpClient CookieContainer를 사용했다.
수신 확인은 로컬 PowerShell 창에서 받았고 OTP는 `Read-Host -AsSecureString`으로 입력받았다.
OTP는 메모리에서만 API 요청에 사용했으며 채팅·명령 인자·명령 이력·파일·보고서에 넣지 않았다.
복호화용 임시 BSTR은 사용 후 지웠다. 실제 메일 본문을 Resend API로 읽어 코드를 취득하지 않았다.

수신 확인 단계에서 처음 창이 종료되어, 테스트가 만든 동일 익명 JDBC 세션을 읽기 전용으로 찾아
브라우저 nonce 해시와 ACTIVE 발급의 바인딩을 대조한 뒤 기존 쿠키·challenge를 메모리에서 복구했다.
서버의 로그인 우회·가짜 인증·코드 강제 설정·DB verifier 수정은 하지 않았다.

## 후속 HTTP 요청의 인증 복원

인증 쿠키로 별도 후속 HTTP 요청을 수행했다.

- 새 CSRF GET: 200.
- 인증된 상태에서 이메일 verify 경로 재진입: 409 LOGOUT_REQUIRED. 임의 사용자 교체가 거절됐다.
  이 요청에는 실제 OTP를 다시 사용하지 않았고 추가 메일도 보내지 않았다.
- 동일 보호 경로 `/__live_verification_protected_probe__`: 익명 401 → 로그인 후 404.
  Spring Security 통과 이후 핸들러가 없어 404가 나는 경로이며, 성공한 업무 API로 표현하지 않는다.

현재 구현에는 로그인 사용자 조회 같은 보호된 업무 API가 없으므로 그 업무 응답까지 검증하지는 못했다.
대신 기존 보안 필터의 보호 경로 처리, 실제 컨트롤러의 인증 세션 판별, JDBC Context·metadata 재조회로
다음 요청에서 인증이 복원됨을 확인했다. 테스트를 위해 제품 API를 추가하지 않았다.
90일 경과를 실제 대기하거나 10분 경계 테스트를 이번에 다시 실행한 것은 아니다.

## 발견 문제·해결

1. 첫 발송 요청 503: 계정/인증 세션 생성 없이 FAILED로 닫혔다.
   provider 상세 응답을 저장하지 않고 발송 전용 키의 로그 조회도 제한되어 최초 원문 오류는 확정하지 못했다.
   사용자가 발신 주소를 수정한 후 별도 승인한 요청은 202로 회복됐다. 제품 결함으로 단정하거나 코드를 수정하지 않았다.
2. 로컬 점검 도구의 기본 샌드박스에서 소켓/프로세스 접근이 제한되어 서버 중지로 잘못 판단했다.
   허용된 읽기 점검으로 기존 서버가 실행 중임을 확인했다. 중복 기동은 포트 충돌로 종료됐으며 추가 메일은 없었다.
3. 원본 서버 로그 출력은 비밀정보 노출 위험으로 자동 승인 검토에서 거절됐다.
   원본을 출력하지 않고 기동 상태·오류 클래스·HTTP 상태만 검사하는 방식으로 진행했다.
4. 최초 수신 확인에서 대문자 YES만 수락하는 임시 도구 때문에 창이 종료됐다.
   재발송 없이 동일 발급/세션 복구 도구를 준비하고 대소문자·Y를 허용했다.
5. 복구 도구가 쿠키를 Base64로 가정해 첫 검증이 401이었다.
   실제 AbsoluteExpiryCookieSerializer는 useBase64Encoding=false였다. 임시 도구만 고쳐
   같은 원본 세션 쿠키로 다시 입력받은 뒤 204가 됐다. 오답 예산이나 DB 상태를 임의로 초기화하지 않았다.

이번에는 승인된 실메일 E2E만 실행했고, 앞서 통과한 자동화 82개를 새로 실행했다고 보고하지 않는다.

## 정리·변경 파일·최종 상태

- 이번 서버·입력 창·JDBC 감사 프로세스를 종료했고 잔여 프로세스 및 18080 리스너는 0건이다.
- Overload PostgreSQL은 작업 시작 전과 같은 중지 상태로 되돌렸다. 컨테이너/볼륨은 삭제하지 않았다.
- 생성된 사용자·20개 운동·설정·인증 세션 및 Flyway/OTP 이력은 `overload-local_postgres_data`에 보존했다.
- 기존 7개 컨테이너 ID/실행 상태와 7개 볼륨 목록이 최종적으로 원래와 동일하다. 타 프로젝트는 변경하지 않았다.
- 프로세스 실메일 활성화는 종료됐고 `.env`의 OTP_EMAIL_ENABLED=false를 최종 확인했다.
- 임시 실행 도구·추출 라이브러리·원본 로컬 로그는 검증 후 정리했다. 비밀값 없는 결과는 본 문서에 남겼다.
- 변경 파일: ignored `.env`의 빈 HMAC 키 보완, 사용자에 의한 발신 주소 수정, 신규 본 보고서.
  제품 소스·빌드 설정·마이그레이션·기존 정책 문서는 변경하지 않았다.
- 최종 Git HEAD는 `766f3a260e2d091d930fc2d519414dbe2b851708`이다. 신규 본 보고서만 untracked이며 staged 0건이다.
  `.env`는 Git ignored다. Commit·Push는 수행하지 않았다.

추가 발송은 필요하지 않으며 자동으로 실행하지 않는다. 007-1C-3은 시작하지 않았다.
